# Window activation ownership

Decision: EXTEND the existing AppDelegate and ContextSettingsController at their source responsibilities. Keep the native window, menu, single LaunchServices owner and background LaunchAgent. Do not add polling, permission prompts, synthetic focus events or an alternate launcher/state machine.

Confirmed source defects in 0.6.14: applicationShouldHandleReopen unconditionally called chooseProject even for an inactive/background reopening. An asynchronous focus/deep-link lookup completion called present, which again ordered the window front and force-activated the application. A window closed or left in the meantime could therefore be raised again. Existing timer, usage refresh and Codex lifecycle callbacks do not themselves call the presentation entry point. Historical logs did not record activation reasons, so they cannot attribute every user-reported occurrence.

New contract: only an explicit synchronous context/usage/menu opening activates the window. Inactive reopens remain background; an already activated foreground reopen can open settings. Target lookup completion only updates the existing model, without constructing, ordering or activating a window. Use AppKit's cooperative activate request instead of ignoringOtherApps. Record reopening acceptance/rejection and explicit window-open reasons through the native unified logger, with no titles, paths, messages, account data or credentials.

The installer accepts --background for this maintenance update: it still restarts the companion through the existing single LaunchServices owner, but does not execute the normal post-install foreground settings command. No main-Codex restart is performed.

Validate inactive-reopen rejection, asynchronous target updates without a window, unchanged synchronous context/usage opening, native manual/menu launch, package/single-process ownership and preserved main-Codex files/configuration. Long-term event attribution remains observation, not a claim inferred from a unit pass.

Local result: v0.6.15 installed through --background. 56 Swift, 50 Python and 76 Node checks passed without skips. Finder opened the existing desktop launcher and the real v0.6.15 settings window appeared; its close action worked. Replaying the existing LaunchAgent on the running background process emitted "Ignored inactive application reopen" in the installed application's unified log. Only one companion process remains, with --background. The main-Codex PID/start time, global config, official Codex/Node binaries and three saved conversation settings hashes are unchanged. Native CUA inventory timed out while the companion had no settings window; that timeout is not asserted as a screenshot or foreground-state proof. Historical user-reported episodes still cannot all be attributed retrospectively.
